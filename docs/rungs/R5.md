# Rungs R5 and R6: per-thread state in registers

Built because the diagnostic run ([`LOG.md`](../../LOG.md), "R3 diagnosis") put 93% of R3's wait per instruction on the load/store path, all of it per-thread local memory, with no register spilling reported. R5 and R6 remove the arrays that I suspect are responsible. That suspicion comes from reading the code, so these rungs are an experiment on it, not a fix for a proven cause.

## What changes

Two things in the hot loop were indexed at run time, which makes the compiler keep them in per-thread local memory:

- **The random generator's buffer.** `PhotonRng` holds the four words of the current Philox block in an array and reads them at a run-time index. `RegPhotonRng` yields the identical stream from four scalars that shift down as they are used, so nothing is indexed.
- **The per-layer accumulator.** R1 and R3 keep one running sum per layer in an array indexed by the packet's layer. R5 and R6 keep a single register for the layer the packet is in, publish it to the global total when the packet changes layer, and publish what is left when it ends. A photon that stays in one layer still makes one global add.

The rungs differ only in how threads are used, so together with R1 and R3 they form a two-by-two comparison:

| | arrays in local memory | registers |
|---|---|---|
| one photon per thread | R1 | **R5** |
| persistent lanes that relaunch | R3 | **R6** |

R5 against R1 and R6 against R3 isolate the effect of the registers; R6 against R5 isolates the relaunch once the memory problem is out of the way. R3 against R1 was already measured.

R0, R1 and R3 are untouched: the new rungs are separate kernels, and the random generator became a template parameter of the physics, so the existing instantiations deduce `PhotonRng` and compile to the same code. The continuous-integration build prints each kernel's registers, stack frame and static count of local-memory instructions, and R1's and R3's did not change.

## Why it is correct

- The two generators agree word for word over 100,000 draws for ids and seeds above 2³² (`tests/cpp/test_philox.cpp`).
- The accumulator is tested directly: absorb in layers 0, 1, 0 and end, and layer 0 must receive both of its partial sums (`tests/cpp/test_gpu_emulation.cpp`).
- R5 has the same events, R_d, T_t and depth profile as R1, and agrees with the CPU engine on events exactly and on absorbed weight to the bound used for R1 (float rounding of at most a photon's weight). This is checked on the three-layer case, where the accumulator changes layer often, and on the single-layer benchmark tissue.
- R6 with one lane is R5 bit for bit, and under round-robin and shuffled interleavings gives the same events per batch and sums to double rounding; the shared photon counter ends at exactly `photons + lanes`.
- Breaking the accumulator (not publishing at a layer change) or the generator (a shift error) makes these tests fail.

## What the compiler produced (static, not a measurement of speed)

From the continuous-integration build for the T4 (sm_75) with the CUDA 12.0 toolkit from the Ubuntu package; Colab has CUDA 13.0, so the real counters decide:

| Kernel | Rung | Registers | Stack frame | Static local loads / stores |
|---|---|---|---|---|
| `photon_kernel` | R0, R1 | 51 | 224 B | 46 / 103 |
| `persistent_kernel` | R3 | 37 | 272 B | 72 / 125 |
| `regs_kernel` | R5 | 50 | 32 B | 6 / 4 |
| `persistent_regs_kernel` | R6 | 47 | 32 B | 6 / 4 |

The static counts include code that never runs (the maths library's slow paths, which force a small frame), so they show that the arrays are gone from the code, not what the kernels do at run time.

## What is measured

Same as before: validation, agreement with the CPU on identical photons, and throughput with **R1 run before and after the others in the same session**. The hardware counters that decide it are the dynamic local-memory instruction counts, the stall breakdown and the L1 hit rate, for R3 against R6.

## What would count as a surprise

The local-memory instructions could vanish and the run time not move, which would say the limit is elsewhere (the digest's other rows would show where). That is what happened for R1 (see Outcome). Registers per thread rise from 37 to 47 for the persistent kernel; occupancy is still limited by warps per multiprocessor, but the counters will show it. Either outcome is a result.

## Outcome

Both rungs are correct and agree with the CPU. R5 took 10.059 s and R6 10.052 s, equal to R1's 10.060 s to 0.1%, while R3 took 10.764 s. So state in registers recovers R3's loss (R6 is 7.1% faster than R3) but does not make R1 faster: local memory slowed R3 but was not what limited R1. What R1, R5 and R6 share, and which sets their run time, is not identified; the per-event depth-profile atomic is the leading candidate. Numbers and the reading are in [`LOG.md`](../../LOG.md) and the README.
