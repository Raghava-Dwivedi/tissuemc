# Rung R8: combine the lanes that share a bin

Built because of what R7's counters showed ([`LOG.md`](../../LOG.md), "R7 counters"): with the L2 hot spot gone, R7's remaining cost is the compare-and-swap loops that update its shared-memory copy of the depth profile. They run about 19 iterations per intended add, add 5.1 billion warp instructions (1.29×) and six times the divergent branches, and keep the double-precision pipe 77% busy. The cause is lanes of one warp adding to the same few bins in the same instruction and retrying against each other.

## What changes from R7

When a lane absorbs weight, it first finds the lanes of its warp that are executing the same instruction and have the same depth bin (`__match_any_sync`). Those lanes sum their weights by reading each other's values (`__shfl_sync`), and the lowest lane of each group makes **one** add of the group's total. A warp with eighteen active lanes spread over a handful of bins now makes a handful of adds instead of eighteen competing ones, and a lane never retries against another lane of its own group. The radius profile, which is added to at most once per photon, is left alone.

What is computed does not change: the same weights reach the same bins. The group's weights are summed in `float` (at most 32 values of similar magnitude, a rounding no worse than the per-photon float sums validated since R1) and the group total is added to the `double` bin.

Everything else is R7: persistent lanes, state in registers, a private copy of the profiles per warp in shared memory, one flush per block.

## Why it is correct

- The algorithm is written against a small interface for a warp (`lane`, `activemask`, `match_any`, `shfl`, `add`), and the host tests run it on a model of 32 lanes in lock step: on 500 random warps with random active masks and skewed bins, and on the edge cases (all lanes in one bin, all in different bins, one active lane, inactive lanes that carry the same key), the table equals the plain sum, there is exactly one add per distinct bin, each made by the lowest lane of its group. Dropping a lane from the sum or electing the wrong leader makes these tests fail.
- The CUDA intrinsics themselves cannot run on the host. They are checked on the GPU, where `tissuemc-cross-engine` compares the depth and radius profiles with the CPU on identical photons (limits fixed before any run) and the validation suite passes.
- The host fallback for the tally (no warp on the host) is plain adds, so the lane's other tallies are checked bit for bit against R7's structure in host emulation.

## What is measured

Validation, the comparison with the CPU including the profiles, and throughput with R7, R8, the profiles-off diagnostic (the target) and R8 again in one session. The counters that decide it are R7's own: shared-memory atomic iterations (633 million in R7), double-precision pipe use, extra warp instructions and divergent branches.

## What would count as a surprise

The aggregation costs instructions of its own: a match, a loop of shuffles over the group, and a leader election. If the groups are mostly of one lane, it removes few retries and adds overhead, and R8 could be slower than R7; the counters would show many shuffle instructions and little drop in loop iterations. If it works, the loop iterations, the double-precision pipe and the divergent branches should all fall together, since they share one cause; if only some fall, the cause was more than one thing.
