# Rung R0: the naive baseline

Every later rung is measured against this one, so it is deliberately simple.

## What it does

- **One thread per photon.** A single launch covers all photons (in chunks of 2²⁶ per launch). Thread *i* simulates photon *i* from launch to death, using the same random stream `(seed, i)` as the CPU engine.
- **Float32 transport.** The physics is the same header the CPU engine runs, instantiated in `float`. The float32 CPU path (`--precision float32`) is the local stand-in for it.
- **Global atomic tallies.** Each photon adds what it scores straight into arrays in GPU global memory with `atomicAdd`: reflectance and transmittance per batch, absorption per batch and layer, and the depth and radius profiles.
- **Running totals are `double`.** Hardware atomic add on `double` needs compute capability 6.0, which a T4 has. This is naive but correct. A `float` mode exists (`--gpu-tally float32`) to show why it is not safe: see below.
- **Batches match the CPU's.** Batch *b* covers the same photon ids as on the CPU, so per-batch results can be compared directly.

## What to expect (a prediction to check, not a result)

1. **Warp divergence.** Photons live for very different numbers of steps: some end within a few dozen events, others take thousands. The 32 threads of a warp run in lockstep, so each warp is held up by its longest-lived photon while the others idle.
2. **Atomic contention.** Every photon adds to the same few hundred depth and radius bins, so thousands of threads queue on the same memory addresses.
3. **Float32 totals lose small additions.** A running total of 2²⁴ or more cannot absorb an addition of 1; more generally an addition smaller than half the last digit of the total vanishes. Absorbed weight (many small additions into a large total) is hit first. Measured on the host with this repository's own kernel body: absorbed weight is fine up to about 10⁴ photons per batch, noisy at 10⁵, and 1.6% too low at 4×10⁵ photons per batch.

## What is measured

- **Validation** on the same cases and rules as the CPU engine (`tissuemc-validate --engine cuda`).
- **Agreement with the CPU on identical photons** (`tissuemc-cross-engine`): totals, per-batch sums and event counts, against limits fixed before any GPU run.
- **Throughput:** million events per second and photons per second, from CUDA-event kernel time, median of 5 repeats after a warm-up (`tissuemc-bench --engine cuda`).
- **The float32-totals demonstration**, run on the GPU.

## What the numbers can and cannot show

- Kernel time excludes setup and copies, which are small for this workload.
- The CPU figures in the results come from a different machine, so any ratio is context, not a like-for-like speedup.
- Nothing here says R0 is a *good* kernel. It is the reference point the later rungs improve on.
