# Rung R3: photon relaunch (persistent lanes)

Built before R2 (shared-memory histograms) because R1's hardware counters show warp divergence, not memory traffic, as the largest loss: memory throughput 14%, L2 12%, and only 4.75 of 32 lanes active per warp instruction. R2 stays in the ladder and is re-measured afterwards.

## What changes from R1

In R0 and R1 each thread simulates one photon from launch to death. Photons here live very different numbers of steps (median 226 events, 90th percentile 7,386, maximum 18,406), and the 32 lanes of a warp run in lockstep, so a warp is held up by its longest photon while the other lanes sit idle.

R3 keeps R1's scoring (per-photon sums, published once when the photon ends) and changes how threads are used:

- A **fixed set of resident threads** is launched: as many blocks as can be resident on the GPU at once (from the CUDA occupancy calculator), never more lanes than photons. On a T4 that is at most 40 multiprocessors × 1,024 threads = 40,960; fewer if this kernel needs more registers per thread than R1's, so the profile records the launched thread count and registers per thread.
- Each thread is a **lane** that claims the next unclaimed photon number from one shared counter with an atomic add. When its photon ends, it publishes that photon's sums and claims another. When the counter passes the last photon, it stops.
- A lane does **one hop-drop-spin step per loop iteration**, not one photon per call, so lanes that start a new photon rejoin the others' step instead of waiting for the whole warp to finish its photons.

Photon *i* still uses the random stream `(seed, i)` and counts toward the same batch, whichever lane runs it, so each batch holds exactly the photons it held in R0 and R1.

## Why it is correct

The lane's state machine (`PersistentLane` in `include/tissuemc/gpu_tally.hpp`) is the code the kernel runs, and it compiles for the host, so it is tested there with many virtual lanes advanced one step at a time in round-robin and pseudo-random orders (`tests/cpp/test_gpu_emulation.cpp`):

- One lane reproduces R1 **bit for bit**, so the reuse of a lane (clearing per-photon sums, switching batch) loses nothing.
- Many lanes in any interleaving give identical event counts per batch and sums equal to double rounding.
- The result agrees with the CPU engine on identical photons, with the same limits as R0 and R1.
- The shared counter ends at exactly `photons + lanes`: no photon is claimed twice or skipped, and each lane stops after one failed claim. This includes more lanes than photons.

Deliberately breaking the lane logic (not updating the batch, not clearing the per-photon sums) makes these tests fail. What the host cannot test is the GPU itself: the launch, the occupancy-sized grid and the hardware atomics. Those are checked on the T4 by validation and by the cross-engine comparison, which now includes absorbed weight.

## What is measured

Same as R1: validation, agreement with the CPU on identical photons (for R1 and R3, on R_d, T_t and absorbed weight), and throughput with **R1 run before and after R3 in the same session**. Hardware counters for R1 and R3 come from Nsight Compute, with the number that matters here: average active threads per warp (4.75 of 32 before).

## What the numbers can and cannot show

- Lanes only stay busy while photons remain. Near the end of a run, lanes wait for the last long photons, so the benefit depends on how many photons each lane handles. The benchmark (4 million photons over at most about 41,000 lanes, so about 100 photons per lane or more) is long enough for that tail to be small; the profiler runs use 2 million photons for the same reason, and the 200,000 used for R0 and R1 would not be.
- Higher active-lane counts do not by themselves mean a faster kernel: lanes can still diverge at the branches inside a step (scatter or boundary), and each step now checks whether the lane needs a new photon.

## Outcome

Validated and in agreement with the CPU, but **not faster**: about 5.7% slower than R1 in the same session. Active lanes per warp rose from 4.74 to 21.61 of 32, and each warp waited 4.9× longer between instructions, which roughly cancelled the gain; compute throughput fell to 8.12 %, memory and L2 stayed low. The cause of the long waits is not identified. Numbers are in [`LOG.md`](../../LOG.md) and the README.
